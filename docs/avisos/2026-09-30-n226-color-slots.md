# Aviso: N-226.1/.3, índice de color asignado por el anfitrión (2026-09-30)

Rama `nacho/N-226-host-color-index`. Toca la zona compartida (`network_manager.gd`). **Sube `PROTOCOL_VERSION` de
9 a 10**: el handshake lleva una clave nueva y hay un RPC nuevo en `NetworkManager`, así que un cliente viejo con
un host nuevo (o al revés) se rechaza como "otra versión". Si se fusiona con otra rama que también la suba, usar
el valor mayor + 1. Archivo nuevo de Nacho: `scripts/core/color_slots.gd` (`class_name ColorSlots`, lógica pura).

## Qué cambió

- `NetworkManager.color_slot(peer_id) -> int` (nuevo, público): el índice de color 0..`MAX_PLAYERS`-1 de ese peer.
  El host se lo da a cada uno por orden de llegada: él mismo 0, cada joiner el libre más bajo (el de alguien que
  se fue se reutiliza; los demás no cambian). Es el mismo en todos los peers y se mantiene en un reinicio del host.
  Fuera de sesión, o para un id que el host todavía no anunció, devuelve `posmod(peer_id, MAX_PLAYERS)`, como
  antes: jugando solo el host (id 1) sigue en 1.
- Señal nueva `color_slots_changed(slots: Dictionary)` (copia de `{peer_id: índice}`). `roster_changed` no cambia.
- Handshake (`_peer_authenticating` → `send_auth`): clave nueva `"colors"` con el mapa. El índice se asigna al
  empezar la autenticación, así que el joiner ya trae el suyo; `_handshake_error` rechaza como `"connection"` un
  handshake sin `"colors"` o con un mapa inválido (claves/valores no int, id ≤ 0, índice fuera de rango, índice
  repetido). Si no queda índice libre, el host responde `{"failure": "full"}` (el menú dice "La sala está llena").
- RPC nuevo `_sync_color_slots(slots)`: `@rpc("authority", "call_remote", "reliable")`, canal 0. El host manda el
  mapa entero cuando cambia: al empezar a autenticarse alguien, al completar el join (a todos, también al nuevo:
  su copia del handshake pudo quedar vieja mientras cargaba), al irse alguien y si falla una autenticación
  (`_auth_failed` libera el índice). El cliente lo ignora si no viene del host y lo valida antes de aplicarlo.
- `_end_session()` limpia los índices; `leave_session()` además emite `color_slots_changed` con el mapa vacío.
  Si se va el host, los clientes lo limpian al volver al menú, sin anunciarlo (igual que `roster_changed`).

## Qué falta (N-226.2, otra corrida)

Hoy ningún lector usa `color_slot()`: siguen con `posmod(peer_id, 5)` (`player.gd`, `crew_panel.gd`,
`hud_notices.gd`, `hud_results.gd`, `depot_panel.gd`, `player_voice.gd`, `crew_progression.gd`). Al migrarlos:

- Usar `PALETA[posmod(NetworkManager.color_slot(peer_id), PALETA.size())]`: los índices llegan hasta
  `MAX_PLAYERS - 1` (7) y la paleta tiene 5 colores; del sexto jugador en adelante los colores se repiten sí o sí.
- Escuchar también `color_slots_changed`: en un cliente, el peer nuevo puede aparecer en `roster_changed` un momento
  antes de que llegue su índice (en el host ya está asignado antes de `roster_changed`).
- Solo vs. sesión: jugando solo el host da 1 (lo que daba antes) y en una sala da 0. Si la campaña se guarda por
  color, decidir en N-226.2 si el jugador local offline debería leerse como 0 para no cambiar de color al abrir sala.
- El mapa puede tener un peer que todavía se está autenticando (no está en `peer_ids`): recorrer el roster, no el mapa.
